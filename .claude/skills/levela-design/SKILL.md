# Levela デザインシステム & 制作ディレクション

## このスキルの前提

Levelaの見た目は**もう決まっている**。あなたの仕事は毎回デザインを発明することではなく、
**確定したブランドを正しく当て、作る順番を間違えないこと**。

デザインが崩れる原因はセンス不足ではなく、ほぼ全部これ:

1. 基準を言語化する前に作り始めた
2. 一度に全部作らせた（＝どこを直せばいいか分からなくなった）
3. 1回出力して「できました」と言った

この3つを構造的に防ぐのがこのスキル。

## 作る順番（省略しない）

規模の大小にかかわらずこの順で進む。ユーザーが明示的に「雑でいい」「急ぎだから飛ばして」と
言った場合だけ簡略化し、**何を省いたかを必ず伝える**。黙って飛ばすのが一番まずい。

### 0. 参考を2〜3点集める

作るものと**近い構図・情報密度**の実物を2〜3点。**色とフォントは参考から取らない**（Levela固定なので）。
参考から取るのは「構成の引き出し」だけ — 何をどの順で見せているか、余白の効かせ方、動きの使いどころ。

- 業界が同じものは避ける。丸パクリのリスクを構造的に消せる
- 出力媒体ごとに現物を見る（Web = PC/スマホ、資料 = 投影/配布）。片方だけ見て作ると必ずもう片方で崩れる
- 参考が用意できない場面（内部ツールなど）では、Levela内の既存の近い画面を参考として扱う

### 1. `design.md` を書く

**作り始める前に**、その成果物での判断基準を1ファイルに落とす。
Levelaトークンは固定なので、ここで決めるのは「固定値をこの成果物にどう割り当てるか」:

- 明背景か暗背景か（→ `references/brand.md` のモード選択）
- 赤 `#E50012` を**どの1箇所**に置くか
- 情報密度（余白広めの訴求面か、密度優先の業務画面か）
- 動きを使うか、使うならどこまで

雛形: `assets/design.md`

### 2. `content.md` を書く

**何をどの順で載せるか**を、実際のテキストで。ダミー文で進めると必ずレイアウトが破綻する。
既存資料（PDF・旧サイト・スプレッドシート）があるなら、それを読んで起こす。

雛形: `assets/content.md`

> **1〜2で情報を渡すときは3回に分ける。**
> 全部まとめて渡すと法則性を見失う。「主要面 → 下層/中面 → 別媒体（スマホ・配布版）」の順に、
> 前の結論を保ったまま追記更新していく。

### 3. 「顔」だけを3案

顔 = Webのファーストビュー / 資料の表紙+1枚目 / 図版のメインカット。

- **顔だけ**作る。全体を一気に作らせない
- **3案**出す。1案だけだと比較対象がなく「これでいいのか」を判断できない
- 3案は振り幅を持たせる: ①デザイン優先（余白と印象） ②内容優先（情報を省略しない） ③その中間
- ここが一番難しく、一番効く。時間と品質をここに集中投下する。方向が決まった後は落としていい

### 4. 具体的なフィードバックで2周直す

1発目が良かった試しはない。**2周目で品質が跳ねる**。

- 「いまいち」「もう少し良く」は禁止。**どこが・どうダメで・どうしたいか**を箇所指定で言う
- 悪い例: 「ヒーローがダサい」
- 良い例: 「ヒーローの見出しが3行に折れて締まりがない。2行に収まる文字数に詰めて、
  サブコピーは`#6B5A52`に落として主従を付ける」
- 直しは溜めてまとめて渡す。1個ずつ投げると前の修正が巻き戻る

### 5. 3案から1案に絞って展開

選んだ1案の方向を保ったまま、段階的に広げる。

Web: 主要面の残り → 下層1ページ → 残り全ページ
資料: 章扉1枚 → その章の中面 → 残り全章

**一気に残り全部を作らせない。** 1ページ作って方向を確認してから複製するほうが、
結果的に速い。方向がずれたまま20ページ作ると全部やり直しになる。

### 6. 素材は後から差し込む

構造を先に完成させ、画像はプレースホルダーで進める。

- 素材がなければ生成する。生成時は**参考画像を必ず添付**し、**実写かイラストかを明示**する。これがないと期待から外れる
- ファイル名で配置先が推測できるように命名する（`hero-main.png`, `service-01-consulting.png`）。
  後で一括配置を頼めるようになる

### 7. 出荷前チェックを1回通す

「できました」で終わらせない。`references/checklist.md` を読んで、媒体に対応する項目を実際に確認する。
確認していない項目を「OK」と書かない。

### 8. 資産を残す

`design.md` と `content.md` を成果物と一緒にリポジトリへ（`docs/` 配下）。
セッションが切れても同じ基準で再現できる状態にして初めて完了。

## 媒体ごとの読み替え

トークンは全媒体共通。当て方だけが変わる。詳細は `references/media.md`。

| 媒体 | 「顔」 | 主背景 | 特記 |
|---|---|---|---|
| Web / LP | ファーストビュー | 紙（明） | レスポンシブは別媒体として扱う |
| ダッシュボード | 最上段のKPI帯 | 墨（暗） | 数値の可読性が最優先。装飾を削る |
| スライド (pptx) | 表紙 + 1枚目 | 紙（明） | 和文はYu Gothic。`assets/tokens.py` |
| Artifact | ファーストビュー | 両対応必須 | `artifact-design` スキルも併読 |
| 図版・画像 | メインカット | 用途次第 | 生成時は参考画像＋実写/イラスト明示 |
| Markdown文書 | 見出し構造 | — | 色は使えない。見出し階層と表で構造を作る |

**グラフ・チャートを作るときは `dataviz` スキルを併読する。**
手法はあちらに従い、**パレットだけ `references/brand.md` のチャート配色に差し替える**。

## 既存コードとの差異（重要）

現状のリポジトリはブランドが3つに割れている。**新規・改修はこのスキルの値に寄せる**。

| 現状 | 扱い |
|---|---|
| スプラッシュ・ロゴ（墨 `#231815` + 赤 `#E50012` + 温白） | **これが正。** 全体をここに寄せる |
| ダッシュボード群（`slate-950` + `teal-300`/`cyan-300` ネオン） | 逸脱。触るついでに墨＋真鍮へ寄せる。全面書き換えは指示があるまでしない |
| pptxスクリプト（紺 `#0B3F66` + 青 `#2D7FF9`） | 逸脱。新規スライドは `assets/tokens.py` を使う |
| `app/globals.css` の `:root` の `#0a0a0a`/`#ededed` | create-next-app の残骸。`body` が上書きしていて未使用 |

既存画面に手を入れるとき、色をこのスキルの値へ寄せる差分は歓迎される。
ただし**依頼範囲外の画面まで勝手に塗り替えない** — 見つけたら報告に留める。
